## Що не так з поточною версією

1. **Промпт підказує відповідь.** Розділи «Результат реального запуску» і «Нотатка про слабкий промпт» — це метадані для людини, а не інструкція для агента. Агент, який отримає їх разом із задачею, уже знатиме про ваду в `splitInstallments` і просто відтворить фікс. Ці розділи краще тримати в окремому файлі, наприклад `add-tests.notes.md`.
2. **Промпт застарів.** Вада вже виправлена, тож тест `100/3` тепер одразу зелений. Розділ про ваду сформульований так, ніби вона ще є, а `version: 1` прив'язана до стану коду до фіксу.
3. **Немає очікуваних значень.** Наприклад, «Тест для `discountPercent=100`» не каже, що має вийти. Агент зафіксує в тесті те, що функція повертає зараз, а не те, що правильно. Тест, який просто записує поточну поведінку, не знайде ваду.
4. **Не визначено, що вважати «реальною вадою».** Немає критерію, де вада, а де дизайнерське рішення. Наприклад, `"-$12.34"` чи `"($12.34)"` для від'ємних сум — це питання до власника коду, а не вада.
5. **Перевіряється конкретний масив, а не правила.** Неважливо, чи буде `[34,33,33]` чи `[33,33,34]`. Важливі правила, які мають виконуватися завжди: сума частин збігається з загальною, кількість частин правильна, різниця між частинами ≤ 1.
6. **Не сказано, що робити з некоректним входом:** `parts=0`, від'ємні `parts`, `discountPercent>100` або `<0`, від'ємні `hours`, `NaN`, нецілі центи. Агент може додати `throw`, а це зміна контракту, яку промпт формально забороняє.
7. **Немає доказу «червоний → зелений».** Фікс дозволено, тільки якщо «тест довів» ваду, але не вимагається показати, що тест падав до фіксу.
8. **Немає захисту від послаблення тестів.** Не заборонено правити старі тести, ставити `.skip` чи `.only`, послаблювати перевірки.
9. **Друкарська помилка:** `center=0` замість `formatMoney(0)`.
10. **Stop-правило неповне.** Не сказано, що робити, якщо фікс вимагає зміни API або вимоги неоднозначні, і скільки спроб фіксу допустимо.

## Покращений промпт (тільки те, що отримує агент)

```markdown
---
name: add-tests
purpose: Розширити тестове покриття app/src/quote.ts крайовими випадками
version: 2
---

# Тести для quote.ts

## Роль
Senior TypeScript-розробник. Пишеш тести (vitest), що перевіряють правила
домену, а не фіксують поточну поведінку.

## Мета
Додати до `app/src/quote.test.ts` тести на крайові випадки для
`estimateTotalCents`, `splitInstallments`, `formatMoney`. Якщо тест виявить
порушення правил домену, виправ його мінімальним дифом.

## Контекст
- Під тестом: `app/src/quote.ts`. Існуючі тести: `app/src/quote.test.ts`.
- Запуск: `cd app && npm test` (vitest).
- Читай лише ці два файли. Решту `app/` не досліджуй.

## Правила домену (джерело очікуваних значень)
1. Усі суми — цілі числа в центах. Будь-який результат у центах — ціле число.
2. `splitInstallments(total, parts)`: `length === parts`; сума елементів
   `=== total`; `max - min <= 1`.
3. `estimateTotalCents` з `discountPercent=100` → `0`; з `hours=0` → `0`.
4. `formatMoney`: формат `"$D.CC"`, рівно 2 знаки центів; від'ємні — `"-$D.CC"`.

Очікуване значення кожного тесту виводь з цих правил. Якщо правило не
визначає результат (напр., куди йде залишок, режим округлення .5) — перевіряй
лише правила, а не конкретне значення.

## Обов'язкові кейси
- `estimateTotalCents`: hours=0; discount=0; discount=100; дробовий проміжний
  результат; округлення рівно посередині (.5); дробовий відсоток (напр. 33.33).
- `splitInstallments`: перевірка правил із п.2 на входах
  100/3, 1/3, 2/3, 0/5, 7/7, 1/1, 90000/3, -100/3.
- `formatMoney`: 0, 5, -5, -1234, 123456789.

## Некоректний вхід
parts ≤ 0, discount < 0 або > 100, hours < 0, NaN, нецілі центи:
НЕ додавай валідацію і НЕ змінюй поведінку. Опиши поточну поведінку в розділі
«Питання до власника» у звіті.

## Що вважається вадою
Лише порушення правила домену з розділу вище. Усе інше (стиль формату,
вибір позиції залишку) — питання до власника, не вада.

## Обмеження
- Змінювати можна лише `app/src/quote.test.ts`; `app/src/quote.ts` — тільки
  після доведеної вади (див. процес).
- Не змінюй публічний API, `package.json`, конфіг vitest, не додавай залежностей.
- Не змінюй і не видаляй існуючі тести; без `.skip`/`.only`/`.todo`/snapshot.

## Процес при знайденій ваді
1. Запусти тести, збережи вивід падіння (червоний).
2. Внеси мінімальний фікс у `quote.ts`.
3. Переконайся, що старі тести дають ті самі результати.
4. Максимум 2 спроби фіксу. Не вийшло, або фікс вимагає змінити API — зупинись
   і опиши проблему.

## Acceptance criteria
- [ ] Усі обов'язкові кейси покриті; очікувані значення виведені з правил домену.
- [ ] Для `splitInstallments` перевіряються правила, а не конкретні масиви.
- [ ] Якщо `quote.ts` змінено — у звіті є вивід падіння ДО фіксу.
- [ ] Існуючі тести не змінені; немає `.skip`/`.only`/snapshot.
- [ ] `git diff --stat` показує лише дозволені файли.
- [ ] `cd app && npm test` — усі тести зелені.

## Формат відповіді
1. Таблиця тестів: назва | вхід | очікування | на якому правилі базується.
2. Вади (якщо є): файл:рядок, вхід, фактичний vs очікуваний результат,
   червоний вивід, diff фіксу, чому він мінімальний.
3. Питання до власника (некоректні входи, неоднозначні правила).
4. Вивід `npm test` дослівно: кількість тестів до і після.

## Stop
Після зелених тестів і звіту — зупинись. Без рефакторингу і нових фіч.
Якщо досягнуто ліміту спроб або потрібна зміна API — зупинись і запитай.
```
