# Чек-ліст санітизації даних для роботи з AI

Багаторазовий чек-ліст команди. Перед тим, як вставляти будь-який
клієнтський документ (бриф, лист, вигрузку, тікет) у чат з AI-моделлю —
пройдіть по ньому. Заповнено на основі вправи з `materials/client-brief.md`
→ `docs/sanitized-brief.md`, але документ написаний так, щоб працювати для
будь-якого клієнтського документа, не лише для цього.

## 1. Що шукаємо (світлофор)

| Категорія | Приклади | Куди можна |
|---|---|---|
| 🔴 Секрети | API-ключі, токени, connection strings, паролі, n8n credentials, webhook URL з токеном у query | нікуди; лише out-of-band через env |
| 🔴 PII клієнтів | ПІБ, email, телефон, адреса, месенджер-хендли (Telegram/WhatsApp) | нікуди в публічну модель |
| 🔴 Продакшн-дані | вигрузки таблиць, логи з даними користувачів, реальні суми замовлень | нікуди; замінити синтетикою того самого формату |
| 🟡 Внутрішня комерція | ставка/собівартість, маржа, умови угоди, дедлайни з конкурентним тиском | лише **enterprise/no-train або локальна модель** |
| 🟡 Внутрішня логіка | назви внутрішніх систем, схеми БД, назви гілок/сервісів, деталі інтеграцій | лише **enterprise/no-train або локальна модель** |
| 🟢 Постановка задачі | опис проблеми, обсяг без даних (кількість заявок/тиждень), критерії приймання | будь-яка модель, зокрема публічна |

## 2. Як маскуємо

- **redaction** — прибрати повністю, без сліду форми: `<REMOVED>`.
  Приклад: месенджер-хендл клієнта в брифі → просто прибраний, а не
  замінений на вигаданий хендл (не потрібен для задачі взагалі).
- **masking** — лишити форму, прибрати значення:
  телефон виду `+380 (XX) XXX-XX-XX` — цифри коду оператора й номера
  приховані, формат лишається впізнаваним. Для connection string
  (`postgres://user:••••@host:port/db`) маскування форми зазвичай
  недостатньо — навіть без реального пароля рядок видає хост і схему
  БД, тому справжній connection string іде категорією 🔴 і не
  маскується частково, а виноситься out-of-band цілком (нижче), без
  жодної його частини в документі.
- **synthetic** — замінити правдоподібним вигаданим того самого формату:
  ПІБ клієнта → `[CLIENT_1]`, три рядки вигрузки замовлень → три вигадані
  рядки з тими самими колонками (Замовник/Телефон/Адреса/Сума) і сумами
  того самого порядку величини.
- **out-of-band** — секрет не потрапляє в текст узагалі, лише посилання
  на нього: `<SECRET_OUT_OF_BAND>`. Це стосується всього рядка з таблиці
  credentials (CRM API key, Slack Bot Token, Airtable PAT, prod webhook,
  Postgres connection string) — не намагайтесь маскувати частину ключа
  (напр. лишаючи перші символи як "для впізнаваності"), просто виносьте
  геть увесь рядок, без жодного фрагмента реального значення.

**Правило:** після маскування задача має лишатись зрозумілою. Якщо модель
більше не розуміє, що робити, — ви замаскували зайве. Перевірка: дайте
результат колезі, що не бачив оригінал — він має зрозуміти, що і навіщо
автоматизувати, без жодного реального контакту, ключа чи суми.

## 3. Перед тим, як вставити в модель

- [ ] Пройшов пошуком по: `key`, `token`, `secret`, `password`, `postgres://`,
      `xoxb-`, `pat`, `@` (email/handle), `+380` (телефон), `sk-`.
- [ ] Немає жодного справжнього телефону / email / ПІБ / месенджер-хендлу.
- [ ] Вигрузки замінені синтетичними рядками того самого формату й того
      самого порядку величини (кількість колонок, приблизна сума).
- [ ] Секрети — лише через env на етапі запуску, не в промпті й не у
      файлі, який іде в модель.
- [ ] Комерційні числа (ставка/собівартість/маржа) прибрані або позначені
      `<INTERNAL>`, а не округлені/замасковані наполовину.
- [ ] Обраний інструмент/tier відповідає **найвищій** категорії, що
      залишилась у документі (якщо є хоч один 🟡-рядок — весь документ іде
      лише в enterprise/no-train або локальну модель, а не в звичайну
      підписку).
- [ ] Задачу все ще можна виконати за цим документом без доступу до
      оригіналу (тестове читання "збоку").

## 4. Інструмент під категорію

| Категорія | Інструмент / режим | Чому |
|---|---|---|
| 🟢 | Будь-яка підписка, зокрема звичайна/споживча (Claude.ai Pro, ChatGPT Plus тощо) | Дані вже не чутливі — ризик обмежений тим, що й так публічне (постановка задачі) |
| 🟡 | Enterprise-підписка з контрактною no-train угодою (напр. Claude for Work / Team, ChatGPT Enterprise) АБО локальна модель на своїй інфраструктурі | Потрібна контрактна гарантія "не йде в тренування" — це перевіряється в договорі, на відміну від "довіри" звичайній підписці; локальна модель — альтернатива, коли навіть контрактної гарантії недостатньо (напр. вимога клієнта тримати дані у себе) |
| 🔴 | Жодна AI-модель, локальна теж — секрети й PII взагалі не потрапляють у жоден текстовий контекст, який бачить LLM | Секрет, що потрапив у контекст моделі (навіть локальної, навіть "no-train"), вважається скомпрометованим за best practice — ротуйте його. Це стосується і промпту, і будь-яких логів/трейсів запиту |

## 5. Який tier ми обрали для 🟡-даних і чому

Для 🟡-категорії (внутрішня комерція, внутрішня логіка систем) команда
використовує **enterprise-підписку з контрактною no-train угодою**, а не
локальну модель за замовчуванням. Причина: локальна модель усуває ризик
повністю, але для щоденної роботи (не разового аудиту чи одноразової
чутливої задачі) вона програє за якістю виводу та швидкістю ітерації, а
контрактна no-train угода вже дає юридично перевірювану гарантію — провайдер
не використовує ваші запити для тренування і не зберігає їх довше
обумовленого терміну. Локальну модель тримаємо як резерв на випадок, коли
клієнт контрактно вимагає, щоб дані взагалі не покидали периметр компанії —
тоді навіть enterprise-хмара не підходить, і в хід іде self-hosted варіант,
свідомо жертвуючи частиною якості заради цієї гарантії.
