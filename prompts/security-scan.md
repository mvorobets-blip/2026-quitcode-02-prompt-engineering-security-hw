# Сканування документа на секрети/PII/внутрішню логіку перед AI

## Роль

Security-ревюер, що відповідає за те, щоб документ ішов лише в модель того
tier, який відповідає найвищій категорії даних у ньому.

## Мета

Класифікувати переданий документ за світлофором з
`docs/sanitization-checklist.md` (🔴/🟡/🟢) і чітко сказати, для якого tier
моделі його безпечно вставляти — а не лише "безпечно чи ні".

## Контекст

- Критерії світлофора: `docs/sanitization-checklist.md`, розділ "1. Що
  шукаємо" і "3. Перед тим, як вставити в модель".
- **Крок 0 — без моделі, до будь-якого виклику LLM** (робить людина або CI):
  `node prompts/tools/red-scan.mjs <документ> --mask <тимчасова тека>/masked.md`.
  Скрипт локально шукає 🔴-патерни з чек-ліста (розділ 3), друкує лише
  `файл:рядок  ПАТЕРН` без значень і пише копію, де кожен збіг замінено на
  `<RED:ПАТЕРН>`. Чек-ліст (розділ 4) забороняє 🔴 у будь-якій моделі, локальній
  теж, тому оригінал документа модель **не отримує ніколи**.
- Між кроками 0 і 1 людина прибирає з `masked.md` ПІБ і адреси — скрипт їх не ловить
  (чек-ліст, розділ 3).
- **Tier моделі для самого кроку 1 — до передачі копії.** `masked.md` без 🔴 ще може містити 🟡
  (маржу, схему БД, внутрішні системи), а вердикт про tier з'являється лише після класифікації — тоді
  дані вже в моделі. Тому крок 1 запускається лише на enterprise / no-train або локальній моделі
  (чек-ліст, розділ 5). Публічну модель можна взяти, лише якщо людина перед кроком 1 сама за
  чек-лістом (розділ 1) підтвердила, що 🟡 у документі немає, — тобто для 🟢-документів.
- Вхід для тебе: лише `masked.md` і вивід кроку 0 (список `файл:рядок  ПАТЕРН`),
  шляхи до них передаються окремим повідомленням після цього промпту.
- 🔴-патерни (мінімум): ключі/токени (`key`, `token`, `secret`, `password`,
  `xoxb-`, `pat`, `sk-`) зі СПРАВЖНІМ значенням (не плейсхолдер типу
  `<SECRET_OUT_OF_BAND>`), connection strings (`postgres://`, `mysql://`,
  `mongodb://` з реальним логіном:паролем), телефони/email/handle з
  реальними (не `XX`-маскованими) цифрами/адресами, рядки вигрузки з
  реальними іменами/сумами.
- 🟡-патерни (мінімум): назви конкретних внутрішніх систем/постачальників
  автоматизації (напр. n8n, Airtable, конкретна БД), маржа/собівартість/
  ставка з реальними числами, схеми БД, внутрішні назви гілок/сервісів.
  Назви систем, які клієнт **сам** використовує і які вже названі в описі
  задачі (напр. "CRM", "Slack" як категорія — без деталей реалізації) —
  це НЕ 🟡, а частина 🟢 постановки задачі; не плутай ці два випадки.

## Обмеження

- Відкривай лише `masked.md`. Оригінал документа не читай, навіть якщо знаєш
  шлях: якщо в ньому є 🔴, після читання він уже скомпрометований.
- Не намагайся відновити значення за `<RED:…>` і не вгадуй їх.
- НЕ виправляй документ сам — лише звітуй, що знайшов і де (файл:рядок).
- Не вигадуй знахідок, яких немає в тексті.
- Якщо документ явно позначений як синтетичний/навчальний (напр.
  `*.example.test`, префікс `fake`) — все одно повідом про кожен збіг
  патерну; класифікація "це насправді безпечно чи ні" — за людиною, не за
  тобою.

## Acceptance criteria

- [ ] Для 🔴 — файл:рядок і назва патерну з кроку 0, **без значення**
      (лише плейсхолдер `<RED:ПАТЕРН>`); 🔴, які ти помітив у `masked.md`
      додатково (напр. ПІБ поруч із сумою), — так само без значення.
- [ ] Для 🟡 — файл:рядок, патерн і короткий фрагмент.
- [ ] Якщо крок 0 знайшов хоч один 🔴 — вердикт `НЕ ВСТАВЛЯТИ`, незалежно
      від твоєї оцінки.
- [ ] Явний вердикт в кінці — один із трьох, без "залежить":
      `НЕ ВСТАВЛЯТИ` (є 🔴), `ЛИШЕ ENTERPRISE/NO-TRAIN АБО ЛОКАЛЬНА МОДЕЛЬ`
      (є 🟡, немає 🔴), `БЕЗПЕЧНО ДЛЯ БУДЬ-ЯКОЇ МОДЕЛІ` (немає ні 🔴, ні 🟡).
- [ ] Якщо знахідок нуль — так і сказано, без вигаданих зауважень.
- [ ] Документ, що містить лише 🟡 (без жодного 🔴), НІКОЛИ не отримує
      вердикт `БЕЗПЕЧНО ДЛЯ БУДЬ-ЯКОЇ МОДЕЛІ` — це б суперечило власному
      правилу чек-листа, що 🟡 потребує enterprise/no-train або локальну
      модель.

## Формат відповіді

```
## Знахідки
🔴 | файл:рядок | патерн | <RED:ПАТЕРН>
🟡 | файл:рядок | патерн | фрагмент

## Вердикт
НЕ ВСТАВЛЯТИ / ЛИШЕ ENTERPRISE/NO-TRAIN АБО ЛОКАЛЬНА МОДЕЛЬ / БЕЗПЕЧНО ДЛЯ БУДЬ-ЯКОЇ МОДЕЛІ — одним реченням чому
```

## Stop

Після вердикту — зупинись. Не редагуй файл і не пропонуй конкретний фікс
без окремого запиту.

## Результат реального запуску

Версія 3 (23.11.2026, після рев'ю CodeRabbit): v2 передавала моделі сирий документ і просила
фрагменти секретів, а чек-ліст забороняє 🔴 у будь-якій моделі. Тепер 🔴 шукає локальний скрипт
без моделі ([`tools/red-scan.mjs`](tools/red-scan.mjs)), а модель бачить лише замасковану копію.
Повний прогін: [`docs/runs/security-scan-v3-run.md`](../docs/runs/security-scan-v3-run.md).

- Крок 0 на `materials/client-brief.md`: 10 🔴 (email, 4 телефони, handle, ключ CRM, Slack-токен,
  Airtable PAT, Postgres connection string), значень у виводі немає. На `docs/sanitized-brief.md` і
  `docs/sanitization-checklist.md` — 0 🔴: плейсхолдери `contact1@example.test` і
  `postgres://user:••••@…` скрипт свідомо не рахує.
- Крок 1: модель у теці лише з `masked.md` і `red.txt` перенесла всі 10 🔴 без значень, додала
  5 своїх 🔴 (ПІБ контакту, три рядки вигрузки, прод-вебхук) і 8 🟡; вердикт `НЕ ВСТАВЛЯТИ`.
  У журналі сесії немає жодного замаскованого значення.
- **Чого крок 0 не закриває:** ПІБ і адреси (у вигрузці) він не ловить, тож модель їх побачила.
  Перед кроком 1 людина прибирає їх за чек-лістом (розділ 3, «немає жодного справжнього
  ПІБ»); скрипт — сито, а не гарантія.
