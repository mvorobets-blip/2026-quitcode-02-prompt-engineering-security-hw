# Дебаг quote.ts

## Роль

Senior TypeScript-розробник, що локалізує баги в чужому коді без переписування.

## Мета

За описом симптому знайти корінну причину в `app/src/quote.ts`, довести її
падаючим тестом і запропонувати мінімальний фікс.

## Контекст

- Файл: `app/src/quote.ts`.
- Існуючі тести: `app/src/quote.test.ts`.
- Команда тестів: `cd app && npm test`.
- Домен: суми — цілі центи.
- Симптом (вхід): `splitInstallments(100, 3)` — сума елементів масиву не
  дорівнює 100.

## Обмеження

- НЕ чіпай файли поза `app/src/quote.ts` і `app/src/quote.test.ts`.
- Спершу доведи баг тестом, що падає на поточному коді, лише потім правити.
- Фікс — мінімальний диф, без побічних змін API.

## Acceptance criteria

- [ ] Є тест, що падає на немодифікованому коді й відтворює симптом.
- [ ] Пояснено корінну причину: файл:рядок, чому саме тут.
- [ ] Застосовано фікс; той самий тест тепер проходить.
- [ ] `cd app && npm test` зелений повністю (усі тести, не лише новий).

## Формат відповіді

1. Файл:рядок і опис кореневої причини.
2. Тест, що відтворює баг (до фіксу — падає).
3. Диф фіксу.
4. Вивід `npm test` після фіксу.

## Stop

Після зеленого `npm test` — зупинись, не шукай інші баги за межами
заданого симптому.

## Результат реального запуску

Запущено на симптомі "`splitInstallments(100, 3)` не сумується в 100"
(реальний запуск, не оцінка):

- Корінна причина: `app/src/quote.ts`, `splitInstallments` — `Math.round`
  застосовувався до кожного платежу окремо, тому округлення кожного з трьох
  платежів (33.33→33) губило сумарний цент.
- Тест, що відтворює: `expect(splitInstallments(100,3).reduce((a,b)=>a+b,0)).toBe(100)`
  — падав на оригінальному коді (99 ≠ 100).
- Фікс: розподіл залишку (`totalCents - Math.floor(totalCents/parts)*parts`)
  по перших елементах масиву замість округлення кожного окремо (див.
  `add-tests.md`, той самий фікс уже застосований у файлі).
- `cd app && npm test`: 11 тестів пройдено, включно з цим.

### Чи відчули різницю (markdown vs XML)

На цій задачі різниці в результаті не було: обидва діалекти дали
ідентичний висновок (та сама корінна причина, той самий фікс, той самий
`npm test`). XML трохи чіткіше розмежував `constraints`/`acceptance`, коли
секцій багато й вони довгі, але для промпту такого розміру це не дало
відчутної переваги — markdown-версія так само легко читається і людиною, і
моделлю. Різниця може стати помітною на довших/умовнішіших промптах, де
вкладеність тегів явно виграє за однозначністю парсингу.
